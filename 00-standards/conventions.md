# Terraform Conventions

This document is the single source of truth for all naming, tagging, file layout, and code style decisions. Every executing AI and every team member must read this before touching any Terraform file.

---

## 1. Repository layout

```
├── .pre-commit-config.yaml
├── docs/
│   └── adr/                      # Architecture Decision Records
├── scripts/
│   └── tf-validate.sh
├── piaas.yml
└── live/
    ├── staging/
    │   ├── 00-bootstrap/
    │   ├── 10-identity/

    │   ├── 30-dns/
    │   ├── 40-data/
    │   ├── 50-compute/
    │   ├── 60-storage/
    │   ├── 70-observability/
    │   └── 80-eks/               # populated after EKS questionnaire
    └── production/
        ├── 00-bootstrap/
        ├── 10-identity/
        ├── 20-network/
        ├── 30-dns/
        ├── 40-data/
        ├── 50-compute/
        ├── 60-storage/
        ├── 70-observability/
        └── 80-eks/
```

### Per-root file layout (inside each numbered directory)

```
<layer>/
├── backend.tf        # terraform block (required_version + backend)
├── providers.tf      # all provider blocks
├── versions.tf       # required_providers only (no resources here)
├── locals.tf         # env/org locals + common_tags
├── data.tf           # data sources and remote-state reads
├── main.tf           # top-level resource calls (may split into domain files)
├── <domain>.tf       # additional resource files split by AWS service
├── variables.tf      # input variables (prefer locals over variables in root modules)
├── outputs.tf        # cross-layer outputs consumed via remote_state
└── .terraform.lock.hcl  # COMMITTED, locked for linux_amd64 and darwin_arm64
```

Split main resources into domain files when a single `main.tf` would exceed ~150 lines. Examples: `iam.tf`, `vpc.tf`, `eks.tf`, `rds.tf`.

### Module library repo (`<org>-terraform-modules`)

```
<org>-terraform-modules/
├── modules/
│   ├── vpc/

│   │   ├── variables.tf

│   ├── s3-bucket/
│   └── ...
├── tests/

├── .github/workflows/            # lint, test, release
├── .releaserc.json               # semantic-release
└── README.md
```

## 2. Naming conventions

### AWS resource names (physical names)

Pattern: `<org>-<env>-<service>[-<detail>]`

- All lowercase, hyphens only — no underscores in AWS resource names.
- `<env>`: `uat` for UAT/staging, `prd` for production.
- `<service>`: short descriptor (vpc, eks, rds, alb, etc.).
- `<detail>`: optional qualifier (main, private, public, a, b, c).

Examples:

| Resource | UAT name | Production name |
|---|---|---|
| VPC | `<org>-uat-vpc` | `<org>-prd-vpc` |
| EKS cluster | `<org>-uat-eks` | `<org>-prd-eks` |
| DocumentDB cluster | `<org>-uat-docdb-main` | `<org>-prd-docdb-main` |
| State S3 bucket | `<org>-tfstate-uat-<region>` | `<org>-tfstate-prd-<region>` |
| IAM execution role | `<org>-uat-terraform-exec` | `<org>-prd-terraform-exec` |
| KMS alias | `alias/<org>-uat-tfstate` | `alias/<org>-prd-tfstate` |
| ALB | `<org>-uat-alb-main` | `<org>-prd-alb-main` |
| ECR repo | `<org>-<service>` (no env, shared across accounts) | — |

### Terraform identifiers (HCL resource/module labels)

Pattern: `snake_case`, **no environment suffix** (the environment is already the directory).

```hcl
# Good
resource "aws_vpc" "main" { ... }
module "vpc" { ... }
resource "aws_iam_role" "terraform_exec" { ... }

# Bad — env suffix redundant and coupling
resource "aws_vpc" "main_staging" { ... }
resource "aws_iam_role" "terraform_exec_uat" { ... }
```

### State key pattern

```
<env>/<layer>/terraform.tfstate
```

Examples:
- `staging/20-network/terraform.tfstate`
- `production/40-data/terraform.tfstate`

### Module source strings

```hcl
# Private module library
source = "git::ssh://git@<BITBUCKET_HOST>:7999/<PROJECT>/<org>-terraform-modules.git//modules/vpc?ref=v1.3.0"

# Terraform Registry (community modules)
source  = "terraform-aws-modules/vpc/aws"
version = "5.19.0"
```

Always pin external modules to an exact version or tag. No range constraints (`~>`, `>=`) on production-critical modules.

## 3. Tagging

Every AWS resource must carry at minimum these tags, applied via the provider `default_tags` block — not via `merge()` on each resource:

```hcl
provider "aws" {
  ...
  default_tags {
    tags = local.default_tags
  }
}
```

```hcl
locals {
  default_tags = {
    Organization  = var.org_name           # e.g. "acme"
    Environment   = local.env_long         # "staging" or "production"
    ManagedBy     = "terraform"
    Repository    = "<org>-infrastructure"
    Layer         = local.layer            # "20-network"
  }
}
```

Additional per-resource tags (beyond `default_tags`) go directly on the resource:

```hcl
resource "aws_vpc" "main" {
  ...
  tags = {
    Name    = "<org>-${local.env}-vpc"
    Service = "network"
  }
}
```

Rationale: Applying tags via `merge(local.common_tags, {...})` on every resource causes many resources to miss tags when the pattern is forgotten. Provider-level `default_tags` makes the base set non-bypassable.

### Required tag keys and allowed values

| Key | Type | Allowed values |
|---|---|---|
| `Organization` | string | lowercase org short-name |
| `Environment` | string | `staging`, `production` |
| `ManagedBy` | string | `terraform` |
| `Repository` | string | repo slug |
| `Layer` | string | `00-bootstrap` … `80-eks` |
| `Name` | string | per-resource per naming convention above |
| `Service` | string | `network`, `identity`, `data`, `compute`, `storage`, `observability`, `eks` |

## 4. Provider version discipline

A single canonical `versions.tf` template is maintained in the module library repo under `templates/versions.tf`. All root modules copy it verbatim and update it via a single PR when providers are upgraded.

```hcl
# versions.tf — canonical, copy exactly into each root module
terraform {
  required_version = "~> 1.11"

  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "= 5.97.0"    # exact pin
    }
    # Add others only if this root needs them:
    # random = { source = "hashicorp/random", version = "= 3.6.3" }
    # tls    = { source = "hashicorp/tls",    version = "= 4.0.6"  }
  }
}
```

Rules:
- Use `=` (exact) for providers in root modules. Use `~>` only inside reusable modules.
- Commit `.terraform.lock.hcl` generated with:
  ```
  terraform providers lock \
    -platform=linux_amd64 \
    -platform=darwin_arm64
  ```
- A Dependabot (or Renovate) config in the infra repo proposes provider upgrades monthly. One PR upgrades all roots simultaneously.

## 5. Variable and output style

### In root modules (live configs)

- Prefer `locals` over `variable` — root modules run in CI under Atlantis, not called from other Terraform.
- Variables are only used for values that legitimately differ between a `terraform plan -var` invocation and the default (almost never in practice).
- Every `locals.tf` must define at minimum: `env`, `env_long`, `org`, `layer`, `account_id`, `region`, `default_tags`.

```hcl
locals {
  org      = "acme"
  env      = "uat"
  env_long = "staging"
  layer    = "20-network"
  region   = data.aws_region.current.name
  account_id = data.aws_caller_identity.current.account_id

  default_tags = {
    Organization = local.org
    Environment  = local.env_long
    ManagedBy    = "terraform"
    Repository   = "<org>-infrastructure"
    Layer        = local.layer
  }
}
```

### In reusable modules

- Every input must have a `description` and explicit `type`.
- Use `validation {}` blocks for enum-like inputs.
- Never use `any` as a type.

```hcl
variable "environment" {
  description = "Deployment environment. Controls naming and tagging."
  type        = string
  validation {
    condition     = contains(["staging", "production"], var.environment)
    error_message = "environment must be 'staging' or 'production'."
  }
}
```

### Outputs

- Every root module exposes outputs consumed by downstream layers via `terraform_remote_state`.
- `outputs.tf` must be present even if currently empty (prevents "file not found" surprises).
- Document every output with `description`.

```hcl
output "vpc_id" {
  description = "ID of the primary VPC."
  value       = module.vpc.vpc_id
}
```

## 6. Secret handling

- Never store secrets (passwords, tokens, API keys) in `.tf` files, `.tfvars`, or state beyond what is unavoidable (resource ARNs are fine).
- Database master passwords: generate with `random_password`, write to the company secrets tool via a provisioner or out-of-band process — do not store in outputs.
- For secrets the secrets tool already owns, use the appropriate data source to read them at plan time.
- `.tfvars` files containing placeholder values (non-secret) may be committed. Files ending in `.auto.tfvars` or `*.secret.tfvars` are gitignored.

## 7. Import discipline

Always use declarative `import {}` blocks (Terraform 1.5+), never the `terraform import` CLI.

```hcl
import {
  to = module.vpc.aws_vpc.this[0]
  id = "vpc-0abc123def456"
}
```

See `04-operations/import-playbook.md` for the full workflow.

## 8. Commit message conventions

Use [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(20-network): import existing VPC and subnets into state
fix(40-data): correct DocumentDB parameter group family
chore(providers): bump aws provider to 5.97.0 across all roots
docs: add ADR-005 for DocumentDB vs RDS decision
```

Types used in this repo: `feat`, `fix`, `chore`, `docs`, `refactor`, `test`.

## 9. Code quality gates (automated)

Run locally before pushing: `./scripts/tf-validate.sh`

In CI (`piaas.yml`) the pipeline runs:

| Tool | Purpose |
|---|---|
| `terraform fmt -check -recursive` | Format check |
| `terraform validate` | Schema validation |
| `tflint --recursive` | AWS best-practice lint |
| `trivy config .` | Security misconfig scan |
| `terraform-docs .` | README regeneration check |
| `checkov -d .` | Compliance checks |

None of these tools run `terraform plan` or make AWS API calls — they operate offline. Plan and apply are Atlantis-only.
